# Geothority Landing Page + Reputation Upgrade Blueprint

Created: 2026-06-03

This blueprint turns the current direction into an implementation plan for two connected upgrades:

1. Rebuild the landing page around plain-English business outcomes.
2. Add a Brand Capture + Reputation Channel Layer so review requests feel branded, trustworthy, and multi-channel.

The guiding principle: sell the destination first, reveal the machinery only when the visitor asks for it.

## 1. Landing Page Rebuild Blueprint

### Problem

The current landing page is impressive, but it is too busy for a lay business owner. It exposes too much internal machinery too early: AEO, Trust Stack, AI engines, schema, citations, automation tables, comparison logic, and dashboard-style detail.

Most prospects do not need to fully understand every technical layer. They need to quickly understand:

- Can this help people find my business?
- Can this help me get more reviews?
- Can this tell me what to fix?
- Will it save me from becoming an SEO expert?
- Is this worth trying right now?

### Moz-Inspired Pattern To Borrow

Moz does a few things well:

- Simple hero promise first.
- Clear CTA pair.
- Trust band near the top.
- Product/solution categories presented in tabs or short cards.
- Deeper tool details behind "Explore..." links.
- Individual feature bands with one idea at a time.
- Proof/data section after the visitor understands the offer.
- Testimonials and education near the lower page.
- Pricing after the product story is clear.

Geothority should mimic that rhythm, not necessarily Moz's exact visual style.

### New Page Story

Primary page message:

> Get found on Google. Get trusted by AI. Get more 5-star reviews.

Plain-English explanation:

> Geothority scans your business, finds what is holding back visibility, and helps turn happy customers into public proof.

Internal product translation:

- Local SEO becomes "show up better on Google and Maps."
- AEO becomes "get understood and recommended by AI."
- Reputation engine becomes "turn happy customers into Google reviews."
- Trust Stack becomes "know what to fix first."
- Automation becomes "we prepare or handle the work."

## 2. Brand Capture Layer Blueprint

### Goal

Use the existing website scanner to extract enough brand context to personalize customer-facing reputation experiences.

Instead of a customer landing on a generic Geothority page, they should land on something that feels like the business they actually used.

Example:

> Review your experience with Bud's Insurance Agency

With the business logo, brand colors, and a category-appropriate motif.

### Current Starting Point

The scanner already:

- Fetches the business website.
- Parses HTML with Cheerio.
- Extracts title, description, H1, links, images, schema, reviews, NAP, OG metadata presence, and GBP links.
- Produces raw scan data.

Brand Capture should extend this scanner rather than creating a separate crawler.

### Fields To Capture

Create a lightweight brand profile with:

- `business_name`
- `website_url`
- `logo_url`
- `logo_source`
- `primary_color`
- `secondary_color`
- `accent_color`
- `font_family_hint`
- `hero_image_url`
- `service_image_urls`
- `business_category`
- `motif`
- `tone`
- `confidence_score`
- `extraction_notes`
- `manual_overrides`
- `created_at`
- `updated_at`

Suggested table:

`business_brand_profiles`

Ownership should follow user/business ownership patterns already used in the app.

### Extraction Sources

Logo candidates:

- `link[rel='icon']`
- `link[rel='apple-touch-icon']`
- `meta[property='og:image']`
- Header images with alt text containing "logo"
- Image URLs containing "logo", "brand", or business name
- SVG logo in header if present

Color candidates:

- Inline styles on header/logo/nav.
- CSS custom properties, if available.
- Dominant colors from logo/OG image if image analysis is added later.
- Fallback palettes by category.

Hero/service image candidates:

- `meta[property='og:image']`
- First large hero image.
- Images near H1.
- Images with service/category keywords.

Category candidates:

- Schema `@type`
- Page title/description
- H1
- Business profile category, if available
- GBP category, if connected
- Keyword matching from site copy

Motif/tone candidates:

- Insurance: clean, trustworthy, professional, calm blue/green.
- Roofer/HVAC/plumber: bold, practical, local service/trades.
- Med spa: polished, soft, premium.
- Law firm: formal, high-trust, restrained.
- Restaurant: warm, visual, hospitality-forward.
- Dental/medical: clean, clinical, reassuring.

### Safety And Quality Controls

Do not blindly apply scraped assets.

Rules:

- Always provide a neutral Geothority fallback.
- Only use remote images from valid http/https URLs.
- Block suspicious, oversized, or tracking-heavy asset URLs.
- Avoid using low-confidence logos.
- Keep color contrast accessible.
- Limit scraped colors to controlled theme slots.
- Allow manual editing by the business.
- Store confidence and source for every captured asset.

### Business Editing Experience

Add a "Brand Profile" settings card:

- Logo preview and upload/replace.
- Primary/accent color picker.
- Business category selector.
- Tone selector.
- Review page preview.
- Reset to scanner-detected brand.

The default is automatic, but the business can override anything.

## 3. Branded Review Flow Blueprint

### Current Starting Point

The existing reputation flow already avoids sending customers directly to Google as the first step:

- SMS asks for a 1-5 reply first.
- Twilio inbound webhook records the score.
- Scores below threshold become private feedback.
- Scores at or above threshold become `public_review_ready`.
- The `/review/[token]` page is locked unless status is `public_review_ready`.
- Google review link appears as the prominent CTA after the positive branch.

That logic should remain, with one compliance guardrail: low-score customers should be guided into private recovery first, but the product should not permanently hide or block the public Google option. That keeps the flow from drifting into review gating while still making recovery the natural path.

### Upgrade Goal

Move from a mostly SMS-reply flow to a branded pre-review landing experience.

The customer should receive a link like:

`https://geothority.com/review/{token}`

Then see:

> How was your experience with [Business Name]?

If 4-5 stars:

- Thank them.
- Offer suggested review copy if appropriate.
- Show "Share on Google" CTA.

If 1-3 stars:

- Ask what went wrong.
- Collect private feedback.
- Notify the business.
- Create or update a recovery item.
- Emphasize private recovery first.
- After feedback is captured, keep an optional public Google link available so the flow does not selectively prohibit negative public reviews.

### Recommended Customer Page States

State 1: Pre-review rating

- Business logo.
- Business name.
- "How was your experience?"
- 1-5 star selector.
- Optional short feedback box.
- Submit button.

State 2: Positive handoff

- "Thanks. Would you share that publicly?"
- Suggested review snippets.
- Copy button.
- Open Google Reviews CTA.

State 3: Private recovery

- "Thanks for telling us. The owner/team will see this privately."
- Feedback text area.
- Optional contact permission.
- "Send private feedback" CTA.
- Post-submit optional "Still want to post publicly? Open Google Reviews" link.

State 4: Already used

- Friendly thank-you.
- Let positive users still open Google if already eligible.

State 5: Invalid/unavailable

- Neutral, non-leaky error page.

### Branded Theme Application

Use the brand profile to style:

- Header logo.
- Accent colors.
- Button colors.
- Background motif.
- Business category language.
- Email header.
- Review request page.
- Positive handoff page.
- Recovery page.

Keep layout consistent across all businesses. Only theme slots change.

## 4. Reputation Channel Layer Blueprint

### Goal

Support SMS and email without duplicating the review logic.

Channels should deliver the same tokenized pre-review link and use the same branching engine.

### Current Starting Point

Existing facts:

- `reputation_contacts` already has an `email` field.
- Outbound reputation transport currently supports simulated and Twilio.
- Resend is already used elsewhere in the app for email journeys and alerts.

Therefore:

- Email reputation send can reuse Resend.
- Contact schema needs stronger channel preferences and send tracking.
- Reputation requests should record channel-level delivery activity.

### Channel Strategy

Preferred behavior:

- Use SMS when phone is present and customer has not opted out.
- Use email when email is present.
- Use both only when configured and throttled.
- Never send direct Google review links as the first step.
- Always send the Geothority tokenized pre-review link.

### Settings To Add

Add reputation settings:

- `enabled_channels`: `sms`, `email`, or `sms_email`
- `primary_channel`
- `email_template`
- `email_subject`
- `send_both_delay_minutes`
- `max_reminders`
- `reminder_delay_hours`
- `quiet_hours_start`
- `quiet_hours_end`
- `brand_profile_id` if needed

### Contact Fields To Add Or Normalize

Existing:

- `phone`
- `email`
- `opt_out`

Recommended additions:

- `sms_opt_out`
- `email_opt_out`
- `preferred_channel`
- `last_contacted_at`
- `last_reputation_request_at`

### Request/Message Tracking

Current `reputation_message_log` can be extended or complemented with channel details.

Recommended additions:

- `channel`: `sms` or `email`
- `recipient`
- `template_id`
- `provider`
- `provider_message_id`
- `opened_at`
- `clicked_at`
- `delivered_at`
- `bounced_at`
- `complained_at`

Email event webhooks can later update delivery/click/open state.

### Email Message Shape

Subject:

> Quick question about your experience with [Business Name]

Body:

Header:

- Business logo.
- Business name.

Main:

> Thanks for choosing [Business Name]. How was your experience?

CTA:

> Leave quick feedback

Footer:

- Sent on behalf of [Business Name].
- Opt-out link.

The CTA must point to `/review/{token}`, not Google.

### Channel Implementation Plan

1. Add `EmailReputationTransport`.
2. Change transport type from single-provider to channel-aware dispatch.
3. Add `channel` to outbound message context.
4. Use Resend for email.
5. Reuse the same token and review page.
6. Add email fields to manual reputation form.
7. Add channel preference controls.
8. Add send logs per channel.

## 5. Implementation Phases

### Phase 1: Landing Page Rebuild

Outcome:

The public homepage becomes simpler, more appealing, and easier for a normal business owner to understand.

Scope:

- Rewrite hero.
- Reorder sections.
- Add three major wins section.
- Compress technical sections behind "Explore..." CTAs.
- Keep comparison as modal.
- Rewrite pricing around outcomes.
- Reduce dense dashboard/detail surfaces.

Validation:

- Desktop screenshot.
- Mobile screenshot.
- Build passes.
- Hero communicates the offer without AEO explanation.
- No text overlap.
- Main page can be scanned in under 30 seconds.

### Phase 2: Brand Capture Foundation

Outcome:

Every scan can produce a lightweight brand profile.

Scope:

- Extend scanner raw data to include brand candidates.
- Add `business_brand_profiles` migration.
- Add extraction utility.
- Add conservative fallback theme.
- Add confidence scoring.

Validation:

- Works on pages with clear logo/OG image.
- Falls back cleanly on weak pages.
- No unsafe asset URLs.
- Theme has accessible contrast.

### Phase 3: Branded Review Landing Page

Outcome:

Customers see a business-branded pre-review page before any Google handoff.

Scope:

- Add pre-rating state to `/review/[token]`.
- Update API route to record rating and feedback from page submission.
- Preserve SMS reply intake.
- Theme page from brand profile.
- Add positive handoff and private recovery states.
- Keep public-review access available after private recovery to avoid a review-gating pattern.

Validation:

- 5-star page submission unlocks Google handoff.
- 1-3 star submission creates private feedback and makes recovery the primary outcome while leaving an optional public Google link available after submission.
- Existing SMS reply path still works.
- Invalid tokens do not leak request data.

### Phase 4: Email Reputation Channel

Outcome:

Businesses can request reviews by SMS, email, or both.

Scope:

- Add email transport via Resend.
- Add email templates/settings.
- Add email recipient support in manual request form.
- Add channel-aware message logs.
- Add throttling rules.
- Add opt-out handling.

Validation:

- Email sends tokenized pre-review link.
- Email does not send Google link first.
- SMS path remains stable.
- Logs show channel and delivery state.

### Phase 5: Business Editing And Preview

Outcome:

Businesses can control their brand profile and preview the review page.

Scope:

- Brand Profile settings UI.
- Logo override.
- Color picker.
- Category/tone selector.
- Preview panel.
- Reset to detected theme.

Validation:

- Manual overrides persist.
- Bad scraped brand data can be fixed.
- Review page reflects overrides.

## 6. Suggested Build Order

Best order:

1. Rebuild landing page first.
2. Add Brand Capture schema and extraction.
3. Add branded pre-review page.
4. Add email channel.
5. Add editing/preview UI.

Reason:

The landing page improves sales clarity immediately. Brand Capture and email improve product depth after the public story is fixed.

## 7. Success Metrics

Landing page:

- Lower bounce rate.

- Better comprehension in user testing.

Review flow:

- Higher feedback completion rate.
- Higher 4-5 star to Google click-through.
